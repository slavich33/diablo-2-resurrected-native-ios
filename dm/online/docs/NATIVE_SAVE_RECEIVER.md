# Native selected-character filesystem receiver

`NativeServerSaveNamespace` and `NativeSaveCommitCoordinator` supply the strong Swift implementations of the optional C filesystem callbacks. Their registry starts empty; an ordinary offline run remains unbound. The app's online controller does not yet prepare this namespace, install the coordinator or start an admitted game session. No sidecar capability change is made by this implementation.

Namespace construction requires a selected snapshot under exactly `LadderSaveScope.prepareDirectory(root:)`, named `snapshot-<UUID>`. It checks the selected committed D2S and optional sidecar against the independently supplied server download. `prepareBeforeEngineStart` installs only this namespace guard, before host preload, cloud startup or any save mount. It requires no engine tables, signing environment or admission. Those later facts cannot be established from local bytes.

The host records the start of preload/boot and each transactional save mount. A late namespace installation is rejected; changing `DM_SAVE` over a running offline engine cannot change an existing mount. An isolated mount must use the exact prepared root and match its current selected predecessor. Clone/setup failure returns failure without registering an offline read-only fallback. The guard lasts for the process, including after peer detachment.

An isolated mount skips offline stash/settings seeds and the mount-seed callback. Its commits skip all five legacy extension hooks and the independent cloud post-commit hook. The real iOS cloud boot and post-commit functions also return before doing work while isolated. Existing hooks remain installed and ordinary unbound offline behavior is retained. Before admission, the selected D2S/sidecar must remain identical to the downloaded pair; unrelated settings can commit. This is selected-pair isolation, not authorization of an entire snapshot or shared stash.

The coordinator retains the account/ladder parent descriptor and checks its identity on later transactions. Absolute directory components, snapshot/work roots, character folders and files are opened without following symlinks. Files are bounded regular files with one link; reads detect size/time changes. The sidecar is written through a unique exclusive0600 temporary file, fsync, successful close and same-directory rename. A failed close is never blindly retried. This uses the existing working-directory clone/swap transaction; it does not claim additional crash durability for uncommitted work.

## Transaction and generation leases

After constructing a previously verified `CharacterSaveCommitSession`, create the coordinator with that same prepared namespace. `installAdmitted` is an explicit caller action after genuine admission with the remote engine quiescent; it requires the prepared namespace and does not perform admission, select `DM_SAVE`, start a socket or import a character. Metadata is refused before installation. The completion event is filtered to the selected work-file path and is only an observation marker. `receive` forwards this connection's ordered kind10 fragments. A final commit with changed bytes needs both a matching complete metadata record and a completion observation.

The final C gate holds path/mount locks. Write, resize and close use the same path lock, and an isolated commit defers while any save writer remains open. This prevents a still-open HLE writer from changing a file while the coordinator signs or clones it. Offline extension hooks run only in an unbound offline process.

The Swift registry and session recursive leases span prepare through finished, so metadata delivery, invalidation and coordinator replacement cannot change that transaction. A table provider must copy actual native rows/names and pin the **admitted expected generation** before returning a `SaveTableLease`. `NativeItemStatCostCapture.acquireLease(for:expectedGeneration:)` does this without using a fallback name list. A different published generation invalidates the binding instead of silently adopting another schema.

The C pin freezes publication/release of the captured snapshot, not arbitrary engine execution. No copy/name/query may be made by the pinning thread until same-thread unpin. Failed/nested pins hold nothing. The engine environment/lifecycle must independently stay bound; the pin is not a substitute for that requirement. Every prepare/finished path releases its table/session/registry leases.

Preparation independently reads the selected committed predecessor, then the final working D2S. The session produces a signed candidate and the receiver writes it beside the D2S in the same work tree. Both files are reread before clone/swap. On actual commit success it reopens the swapped committed directory and compares exact D2S/sidecar bytes again. Only that readback consumes metadata and advances local history and the namespace baseline. A post-swap mismatch sets a persistent namespace failure and invalidates the session even if the C filesystem returned success. Detachment never re-enables offline hooks or unsigned character commits. `localCommitCount` is local acceptance, never a server receipt.

## Coupled native verification

```sh
python3 dm/online/tools/verify_native_save_commit.py --scratch /path/to/private/scratch
make -C dm/host/tests net-tables
```

The first command builds real host HLE filesystem/capture C and `cloud_ios.m` together with the production Swift receiver, session, CryptoKit signing and iOS native table helper. It executes owned synthetic bytes and an ephemeral key, with no game image, account, device or network. It prepares isolation before mounting, rejects another root before seeds can run, checks mount-clone failure/retry and permits an unchanged pre-admission commit. Tripwires confirm all five legacy hooks, mount seed, post-commit cloud hook and the real cloud boot are skipped while isolated; cloud dependencies are stubs and never perform synchronization.

Three progress commits verify continuous signed history and independent committed-file readback. The same process checks pre-admission character-change refusal, open-writer deferral, missing metadata, clone/swap failure, exact retry signatures, replay, selected-file and parent symlinks, an unchanged offline sentinel and rejection of a changed captured generation. A second process corrupts its own synthetic file after the directory swap; readback rejects it despite C commit success and releases the pin. A third starts an ordinary offline mount, confirms its hooks still run, then rejects late isolation. A fourth detaches a healthy peer and verifies that unchanged signed bytes can still commit while new unsigned changes are deferred and offline/cloud hooks remain excluded. These are real local C/Swift transaction checks, not real gameplay or server admission.

The capture test separately starts a concurrent reload, observes it cannot publish while pinned, then releases and verifies the new generation. It also checks wrong-thread/nested release/query rules and existing failed-capture behavior. ARM64 iOS library/helper typechecking and filesystem/capture C syntax checks are separate from a full app build/install.

## Remaining app/server integration

The actual online startup and packet pump must prepare the verified namespace before any engine preload/boot, bind the expected capture generation after admission, forward metadata and propagate receiver failure into the remote lifecycle. The host retains mounted save roots and unmount is currently a no-op: switching from an already running offline game requires a controlled process restart with offline state preserved. These local guard APIs do not implement that UI/lifecycle transition or disable every possible game-time offline extension.

This receiver validates the selected character pair, not every file in a server snapshot. Shared stash/progress upload, whole-snapshot authorization, server expected versions/receipts, reconnect and server readback need the actual Server Saves contract. Native fingerprint acquisition, remaining protocol/engine work and real iPhone ladder play are not proved here. The explicit linked-codec profile declares support1/format2 independently of game admission; see [ENVIRONMENT_DESCRIPTION.md](ENVIRONMENT_DESCRIPTION.md). No actual app binding or progress upload occurs in these local tests.
